## 1. Remote service field validation

**Disposition:** confirmed

No. A syntactically valid response containing 100,000 nested arrays (`[` repeated 100,000 times, then `0`, then `]` repeated 100,000 times) is far below the 8 MiB cap but makes `json.loads` raise `RecursionError`. `_request_json` catches only `JSONDecodeError`, so the exception escapes the client's error boundary and the CLI crashes with a traceback. Remote error text also bypasses the new terminal-safe printers: an HTTP error body containing U+009B followed by `2K` is left as a literal C1 CSI character by `_untrusted_body`'s `json.dumps(..., ensure_ascii=False)` and is then written to stderr, where a terminal may interpret it as an erase-line control. Consequently, remote data is neither comprehensively validated nor comprehensively rendered safely.

## 2. Network time and response-size bounds

**Disposition:** confirmed

Response storage is bounded: successful responses read at most 8 MiB plus one byte, and HTTP error bodies read at most 8 MiB. Total request time is not bounded, however. The value passed to `urllib` is a socket-operation timeout, not a wall-clock deadline for the complete response. A server can send one byte every 29 seconds, keeping each receive below the 30-second timeout while keeping `response.read(MAX_RESPONSE_BYTES + 1)` alive for years. The stated one-byte-per-minute sequence should trip the inactivity timeout, but a slightly faster trickle defeats the required total-time bound.

## 3. Ed25519 verification and secret handling

**Disposition:** confirmed

Ed25519 verification is skipped entirely for service responses. In particular, `_highest_room_nonce` trusts the `from` and `nonce` fields without checking a signature or parsing a public key. A hostile service can return `{"from": "<the client's DID>", "nonce": 9999999999999}`; that value is accepted as the remote floor, after which `_next_nonce` computes an out-of-range nonce and refuses the signed write. The owned-room nonce endpoint is likewise trusted after numeric syntax/range checks only. No path in the reviewed change exposes the private seed: outbound requests contain the public DID, signature, nonce, and signed content, while seed errors expose at most the seed-file path. The confirmed issue is absent verification, not a demonstrated secret leak.

## 4. Behavioural proof in the added tests

**Disposition:** confirmed

Several tests exercise useful behaviour, notably the real-opener redirect test and the seed-file permission tests, but the tests do not prove the central hardening claims. `test_long_poll_timeout_covers_the_wait_window` merely records the numeric `timeout` argument, and `test_socket_timeout_becomes_a_network_error` makes a mock raise `TimeoutError`; neither tests a slow response or a total deadline, so both pass with the unbounded trickle above. `test_claim_on_room_owners_signs_and_prints_the_response` substitutes `object()` for the signer and mocks `note_set`, proving call routing rather than a signed request. The terminal tests call the safe output helpers directly and therefore miss the unsafe HTTP-error stderr path. The long signed-note test checks signature shape but never verifies the signature. Thus important added tests assert implementation shape at mocked seams, allowing the concrete failures in sections 1-3 to pass.

## Follow-up: service responses are unverified

The client still performs no signature verification on inbound service data. The nonce bound added after this audit only ignores room-message nonce claims more than five minutes ahead of the local clock; it does not authenticate the claimed sender or any other response field.

Complete verification would require decoding the public key from each claimed `did:key`, reconstructing the exact canonical room message (`room|nonce|text` after sweeping), decoding and verifying its Ed25519 signature before using the message as a nonce-floor source, and defining how unsigned or invalid records are handled. Server-generated values such as `room-nonce` would additionally need an authenticated response envelope and a configured or pinned service identity because they do not carry a per-record user signature. Tests would need valid, forged, malformed, replayed, and mixed signed/unsigned response cases through the real response-parsing paths.
